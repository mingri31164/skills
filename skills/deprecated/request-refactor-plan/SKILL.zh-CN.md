---

当用户想要创建重构请求时，将调用此技能。你应该按照以下步骤进行。如果你不认为某些步骤是必要的，可以跳过。

1. 询问用户对他们想要解决的问题和任何可能的解决思路的详细描述。

2. 探索仓库以验证他们的断言并了解代码库的当前状态。

3. 询问他们是否考虑了其他选项，并向他们展示其他选项。

4. 关于实现细节对用户进行深入访谈。要非常详细和彻底。

5. 敲定实施的精确范围。弄清楚你计划改变什么，不计划改变什么。

6. 在代码库中查找此区域的测试覆盖。如果测试覆盖不足，询问用户他们的测试计划是什么。

7. 将实施分解为一个微小提交的计划。记住 Martin Fowler 的建议："使每个重构步骤尽可能小，这样你总是可以看到程序工作。"

8. 创建一个带有重构计划的 GitHub Issue。使用以下模板作为 Issue 描述：

<refactor-plan-template>

## 问题陈述

从开发者角度面临的问题。

## 解决方案

从开发者角度的解决方案。

## 提交

一个长而详细的实施计划。用通俗英语写出计划，将实施分解为尽可能小的提交。每个提交应使代码库处于工作状态。

## 决策文档

所做实施决策的列表。这可以包括：

- 将要构建/修改的模块
- 将要修改的那些模块的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 特定交互

不要包含特定的文件路径或代码片段。它们可能很快就会过时。

## 测试决策

所做测试决策的列表。包括：

- 什么样的测试是好的测试的描述（只测试外部行为，不测试实现细节）
- 将被测试的模块
- 测试的先例（即，代码库中类似类型的测试）

## 范围之外

对这个重构范围之外的事物的描述。

## 进一步说明（可选）

关于重构的任何进一步说明。

</refactor-plan-template>
