# QA 会话

运行交互式 QA 会话。用户描述他们遇到的问题。你澄清，后台探索代码库以获取上下文，并提交耐久的、以用户为中心的、使用项目领域语言的 GitHub Issue。

## 对于用户提出的每个问题

### 1. 倾听和轻度澄清

让用户用自己的话描述问题。最多问**2-3 个简短的澄清问题**，集中在：

- 他们期望的 vs 实际发生的
- 复现步骤（如果不明显）
- 它是一致的还是间歇性的

不要过度访谈。如果描述足够清晰可以直接提交，那就继续。

### 2. 后台探索代码库

在与用户交谈时，在后台启动一个 Agent（subagent_type=Explore）来理解相关区域。目标不是找到修复——而是：

- 了解该区域使用的领域语言（检查 UBIQUITOUS_LANGUAGE.md）
- 理解该功能应该做什么
- 识别用户面向的行为边界

此上下文帮助你写出更好的 Issue——但 Issue 本身不应引用特定文件、行号或内部实现细节。

### 3. 评估范围：单个 Issue 还是分解？

提交之前，决定这是**单个 Issue** 还是需要**分解**为多个 Issue。

在以下情况下分解：

- 修复跨越多个独立区域（例如"表单验证是错的 AND 成功消息缺失 AND 重定向坏了"）
- 有明显可分离的关注点，不同的人可以并行处理
- 用户描述的内容有多个不同的失败模式或症状

在以下情况下保持单个 Issue：

- 它是一个地方的一个错误行为
- 症状都是由同一个根本行为引起的

### 4. 提交 GitHub Issue

使用 `gh issue create` 创建 Issue。不要要求用户先审查——直接提交并分享 URL。

Issue 必须**耐久**——在重大重构后仍然有意义。从用户角度编写。

#### 对于单个 Issue

使用此模板：

```
## 发生了什么

[用通俗语言描述用户经历的实际情况]

## 我期望的

[描述期望的行为]

## 复现步骤

1. [开发人员可以遵循的具体编号步骤]
2. [使用代码库的领域术语，而不是内部模块名称]
3. [包含相关输入、标志或配置]

## 其他上下文

[来自用户或代码库探索的任何额外观察，有助于框定问题——例如"这仅在使用 Docker 层时发生，而不是文件系统层"——使用领域语言但不引用文件]
```

#### 对于分解（多个 Issue）

按依赖顺序（先阻塞者）创建 Issue，这样你可以在"被阻塞于"中引用真实的 Issue 编号。

每个子 Issue 使用此模板：

```
## 父 Issue

#<父 Issue 编号>（如果你创建了跟踪 Issue）或"在 QA 会话期间报告"

## 什么问题

[描述这个特定的行为问题——只是这个切片，不是整个报告]

## 我期望的

[这个特定切片的期望行为]

## 复现步骤

1. [仅针对此 Issue 的步骤]

## 被阻塞于

- #<Issue 编号>（如果此 Issue 在另一个解决之前无法修复）

如果没有阻塞，写"无——可以立即开始"。

## 其他上下文

[与此切片相关的任何额外观察]
```

创建分解时：

- **优先选择多个薄 Issue 而不是几个厚 Issue** —— 每个应该是独立可修复和可验证的
- **诚实标记阻塞关系** —— 如果 Issue B 真的在 Issue A 修复之前无法测试，说出来。如果它们是独立的，两个都标记为"无——可以立即开始"
- **按依赖顺序创建 Issue** 这样你可以在"被阻塞于"中引用真实的 Issue 编号
- **最大化并行性** —— 目标是多个人（或 Agent）可以同时拾取不同的 Issue

#### 所有 Issue 正文的规则

- **不要有文件路径或行号** —— 这些会过时
- **使用项目的领域语言**（检查 UBIQUITOUS_LANGUAGE.md 如果存在）
- **描述行为，而不是代码** —— "同步服务无法应用补丁"而不是"applyPatch() 在第 42 行抛出"
- **复现步骤是强制性的** —— 如果你无法确定，询问用户
- **保持简洁** —— 开发人员应该能够在 30 秒内读完 Issue

提交后，打印所有 Issue URL（附上阻塞关系摘要）并问："下一个 Issue，还是完成了？"

### 5. 继续会话

继续直到用户说完成。每个 Issue 是独立的——不要批量处理。
