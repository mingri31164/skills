# 转为 Issue

使用垂直切片（追踪弹）将计划分解为可独立拾取的 Issue。

Issue 追踪器和分类标签词汇表应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容开始。如果用户传递了 Issue 引用（Issue 编号、URL 或路径）作为参数，从 Issue 追踪器获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索代码库，请这样做以了解代码的当前状态。Issue 标题和描述应使用项目的领域词汇表，并尊重你正在触及的区域的 ADR。

### 3. 起草垂直切片

将计划分解为**追踪弹** Issue。每个 Issue 是一个薄的垂直切片，端到端贯穿所有集成层，而不是一层的水平切片。

切片可以是'HITL'或'AFK'。HITL 切片需要人工交互，例如架构决策或设计审查。AFK 切片可以在没有人机交互的情况下实施和合并。尽可能优先选择 AFK 而不是 HITL。

<vertical-slice-rules>
- 每个切片通过每一层（schema、API、UI、测试）提供一条狭窄但完整的路径
- 完成的切片可以独立演示或验证
- 优先选择多个薄切片而不是几个厚切片
</vertical-slice-rules>

### 4. 测验用户

以编号列表呈现建议的分解。对于每个切片，显示：

- **标题**：简短的描述性名称
- **类型**：HITL / AFK
- **被阻塞于**：哪些其他切片（如果有）必须先完成
- **涵盖的用户故事**：这解决了哪些用户故事（如果源材料有的话）

询问用户：

- 粒度感觉合适吗？（太粗 / 太细）
- 依赖关系正确吗？
- 是否有任何切片应该合并或进一步拆分？
- 正确的切片被标记为 HITL 和 AFK 了吗？

迭代直到用户批准分解。

### 5. 将 Issue 发布到 Issue 追踪器

对于每个批准的切片，将新的 Issue 发布到 Issue 追踪器。使用下面的 Issue 正文模板。这些 Issue 被视为准备好供 AFK Agent 使用，因此除非另有指示，否则以正确的分类标签发布它们。

按依赖顺序（先阻塞者）发布 Issue，这样你可以在"被阻塞于"字段中引用真实的 Issue 标识符。

<issue-template>
## 父级

对 Issue 追踪器上父级 Issue 的引用（如果源是一个现有 Issue，否则省略此部分）。

## 要构建的内容

对这个垂直切片的端到端行为的简洁描述。描述端到端行为，而不是逐层实现。

避免特定的文件路径或代码片段——它们很快就会过时。例外：如果原型产生了一个比散文能更精确地编码决策的片段（状态机、reducer、schema、类型形状），将其内联在这里，并简要说明它来自原型。修剪到决策丰富的部分——不是工作演示，只是重要的部分。
