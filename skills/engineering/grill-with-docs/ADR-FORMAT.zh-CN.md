# ADR 格式

ADR 生活在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录——仅在需要第一个 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{一二三句：上下文是什么，我们决定了什么，为什么。}
```

就这样。ADR 可以是一段。价值在于记录_做了_决策和_为什么_——而不是填写章节。

## 可选部分

仅在它们增加真正价值时才包含这些。大多数 ADR 不需要它们。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策被重新审视时有用
- **考虑的选项** ——仅在拒绝的替代方案值得记住时
- **后果** ——仅在需要指出不明显下游影响时

## 编号

扫描 `docs/adr/` 查找最高现有编号并递增一。

## 何时提供 ADR

必须满足以下全部三个：

1. **难以逆转**——以后改变主意的代价是有意义的
2. **没有上下文会令人惊讶**——未来的读者会看着代码想知道"他们到底为什么要这样做？"
3. **是真正权衡的结果**——有真正的替代方案，你出于特定原因选择了其中一个

如果决策容易逆转，跳过它——你会反转它。如果不令人惊讶，没有人会想知道为什么。如果没有真正的替代方案，没有什么可记录的，除了"我们做了显而易见的事情"。

### 什么符合条件

- **架构形状。** "我们使用 monorepo。""写模型是事件溯源的，读模型被投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库——只是那些需要四分之一时间交换的。
- **边界和范围决策。** "客户数据由客户上下文拥有；其他上下文仅通过 ID 引用它。" 明确的 no 和 yes 一样有价值。
- **偏离明显路径的有意偏差。** "我们使用手动 SQL 而不是 ORM，因为 X。" 任何理性读者会假设相反的事情。这阻止下一个工程师"修复"实际上是刻意的某事。
- **代码中不可见的约束。** "我们不能使用 AWS 因为合规要求。""响应时间必须低于 200ms 因为合作伙伴 API 契约。"
- **当拒绝是不明显时拒绝的替代方案。** 如果你考虑了 GraphQL 并选择了 REST 是因为微妙的原因，记录它——否则六个月内会有人再次建议 GraphQL。
