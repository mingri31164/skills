# 诊断

处理硬性 bug 的规范流程。只有在有明确理由时才跳过阶段。

在探索代码库时，使用项目的领域词汇表来获得相关模块的清晰心理模型，并检查你正在触及的区域的 ADR。

## 阶段 1 — 构建反馈循环

**这就是技能本身。** 其他一切都是机械性的。如果你有一个快速的、确定性的、可由 Agent 运行的通过/失败信号来检测 bug，你就会找到原因——二分法、假设检验和插桩都只是消耗那个信号。如果没有，再怎么看代码也救不了你。

在这里投入不成比例的努力。**要激进。要有创意。拒绝放弃。**

### 构建反馈循环的方法——按大致这个顺序尝试

1. **失败测试**——在触及 bug 的任何接缝处（单元、集成、端到端）。
2. **Curl / HTTP 脚本**——针对运行中的开发服务器。
3. **CLI 调用**——使用 fixture 输入，将 stdout 与已知的良好快照进行 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **回放捕获的跟踪。** 将真实的网络请求/负载/事件日志保存到磁盘；在隔离状态下通过代码路径回放。
6. **一次性测试工具。** 启动系统的一个最小子集（一个服务，被模拟的依赖项），用单个函数调用执行 bug 代码路径。
7. **属性/模糊循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入并寻找失败模式。
8. **二分查找工具。** 如果 bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动、检查、重复"，以便你可以用 `git bisect run` 运行。
9. **差异循环。** 通过旧版本 vs 新版本（或两个配置）运行相同的输入并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人点击，用 `scripts/hitl-loop.template.sh` 驱动 _他们_，使循环仍然是结构化的。捕获的输出反馈给你。

构建正确的反馈循环，bug 就解决了 90%。

### 迭代循环本身

把循环当作一个产品。一旦你有了 _一个_ 循环，问：

- 我能让它更快吗？（缓存设置，跳过无关初始化，缩小测试范围。）
- 我能让信号更锐利吗？（断言具体症状，而不是"没有崩溃"。）
- 我能让它更确定性吗？（固定时间，种子 RNG，隔离文件系统，冻结网络。）

一个 30 秒的不稳定循环比没有循环好不了多少。一个 2 秒的确定性循环是调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。将触发器循环 100×，并行化，增加压力，缩小时间窗口，注入 sleep。一个 50% 的 flaky bug 是可调试的；1% 不是——不断提高复现率直到它可调试。

### 当你真的无法构建循环时

明确说出来。列出你尝试过的方法。询问用户：(a) 访问能复现的环境，(b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的许可。在没有循环的情况下**不要继续进入假设阶段**。

在你相信的循环建立之前不要进入阶段 2。

## 阶段 2 — 复现

运行循环。观察 bug 出现。

确认：

- [ ] 循环产生用户描述的失败模式——而不是恰好附近的另一个不同失败。找错 bug = 找错修复。
- [ ] 失败在多次运行中是可复现的（或者，对于非确定性 bug，以足够高的速率可复现以支持调试）。
- [ ] 你已经捕获了确切的症状（错误消息、错误输出、慢速时序），以便后续阶段可以验证修复是否真正解决了问题。

在复现 bug 之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前，生成**3-5 个排名假设**。单一假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 X 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。"

如果你无法陈述预测，那个假设只是一种感觉——丢弃或锐化它。

**在测试之前向用户展示排名列表。** 他们通常有能立即重新排名的领域知识（"我们刚刚部署了 #3 的变更"），或者知道你已经排除的假设。便宜的检查点，大的时间节省。不要在这里阻塞——如果用户不在，继续按你的排名进行。

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 的一个特定预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**——如果环境支持。一个断点胜过十个日志。
2. **目标日志**——在区分假设的边界处。
3. 永远不要"记录所有内容然后 grep"。

**标记每个调试日志**带有唯一前缀，例如 `[DEBUG-a4f2]`。最终清理变成一次 grep。未经标记的日志保留；已标记的日志销毁。

**性能分支。** 对于性能回归，日志通常是错误的。替代方案：建立基准测量（时序工具、`performance.now()`、profiler、查询计划），然后二分查找。先测量，再修复。

## 阶段 5 — 修复 + 回归测试

在修复之前编写回归测试——但仅当存在**正确的接缝**时。

正确的接缝是指测试在调用点实际发生的真实 bug 模式的位置。如果唯一可用的接缝太浅（单调用方测试而 bug 需要多个调用方，单元测试无法复制触发 bug 的链），那里的回归测试会产生虚假的信心。

**如果没有正确的接缝存在，那本身就是一个发现。** 记录它。代码库架构阻止了 bug 被锁定。将其标记给下一阶段。

如果存在正确的接缝：

1. 将最小化复现转换为在该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 对原始（未最小化）场景重新运行阶段 1 反馈循环。

## 阶段 6 — 清理 + 复盘

在宣布完成之前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或记录了接缝缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 已删除一次性原型（或移动到标记明确的调试位置）
- [ ] 在提交/PR 消息中陈述被证明正确的假设——以便下一个调试者学习

**然后问：什么本可以防止这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、调用方纠缠、隐藏耦合），使用具体细节将工作交给 `/improve-codebase-architecture` 技能。在修复完成后_之后_提出建议，而不是之前——你现在比开始时掌握了更多信息。
