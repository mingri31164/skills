# UI 原型

在一条路由上生成**多个截然不同的 UI 变体**，可通过浮动底部栏切换。用户可以在浏览器中翻转变体，选择一个（或从每个中窃取部分），然后扔掉其余的。

如果问题是关于逻辑/状态而不是某物看起来怎么样——错误的分支。使用 [LOGIC.md](LOGIC.md)。

## 这是正确形状的时候

- "这个页面应该是什么样子？"
- "在承诺之前我想看几个仪表板的选项。"
- "尝试设置屏幕的不同布局。"
- 用户原本会在脑海中花一天时间在三个模糊 mockup 之间选择的任何时候。

## 两个子形状——强烈优先子形状 A

当 UI 原型**碰上应用的其他部分**时更容易判断——真实头部、真实侧边栏、真实数据、真实密度。独自的一次性路由是一个真空：每个变体在隔离中都看起来不错。只要有可行的现有页面托管变体，默认到子形状 A。只有在原型确实没有附近主页时才达到子形状 B。

### 子形状 A — 调整现有页面（首选）

路由已存在。变体在**同一路由**上呈现，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和 auth 都保持——只有渲染交换。这是默认的；除非有特定原因不选它，否则选择它。

如果原型是针对还没有页面的某物但_自然会在一个里面_（仪表板的新部分、设置屏幕的新卡片、现有流程中的新步骤）——那仍然是子形状 A。在主机页面中挂载变体。

### 子形状 B — 新页面（最后手段）

仅在原型化的东西确实没有现有页面可以放在其中时使用——例如全新的顶级 surface，或无法嵌入任何合理地方的流程。

按照项目已有的路由约定创建**一次性路由**——不要发明新的顶级结构。命名时要明显是原型（例如在路径或文件名中包含 `prototype` 一词）。相同的 `?variant=` 模式。

在承诺子形状 B 之前，检查：这个东西真的没有现有页面可以嵌入其中吗？空路由隐藏了填充后会暴露的设计问题。

在两个子形状中浮动底部栏是相同的。

## 流程

### 1. 陈述问题并选择 N

默认为**3 个变体**。超过 5 个不再是截然不同，开始成为噪音——上限在那里。

在原型位置或文件顶部注释中一行写下计划：

> "三个设置页面变体，通过 `?variant=` 切换，在现有 `/settings` 路由上。"

这在用户是否在这里反驳时都有效。

### 2. 生成截然不同的变体

起草每个变体。坚持每个：

- 页面的目的和它可以访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便）。
- 明确的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须是**结构上不同的**——不同的布局、不同的信息层次、不同的主要功能，而不是只是不同的颜色。三个略微调整的卡片网格不是 UI 原型，是墙纸。如果两个草稿太相似，用明确的"不要使用卡片网格"指导重做一个。

### 3. 将它们连接在一起

在路由上创建单个切换器组件：

```tsx
// 伪代码——适配项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形状 A（现有页面）：在切换器上方保持所有现有的数据获取；只有渲染子树按变体改变。

对于子形状 B（新页面）：`.out-of-scope/` 下的临时路由挂载相同的切换器。

### 4. 构建浮动切换器

一个小固定位置栏在屏幕底部中央，包含三部分：

- **左箭头** — 循环到上一个变体（环绕）。
- **变体标签** — 显示当前变体键，如果变体导出名称也显示。例如 `B — 侧边栏布局`。
- **右箭头** — 向前循环（环绕）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的 router——Next 上 `router.replace`，React Router 上 `navigate` 等），以便变体可共享且重新加载稳定。
- 键盘：`←` 和 `→` 箭头键也循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截箭头键。
- 视觉上与页面不同（例如高对比度药丸、微妙的阴影），以便它明显不是正在评估的设计的一部分。
- 在生产构建中隐藏——在 `process.env.NODE_ENV !== 'production'` 或等效检查上控制，以便孤立的原型合并不能将栏运送给用户。

将切换器放在单个共享组件中，以便两个子形状都可以重用。将其放置在项目中共享 UI 所在的位置。

### 5. 交接

显示 URL（和 `?variant=` 键）。用户在他们到达时翻转。有趣的反馈通常是**"我想要 B 的头部和 C 的侧边栏"**——那是他们实际想要的设计。

### 6. 捕获答案并清理

一旦变体获胜，写下哪一个以及为什么（提交消息、ADR、issue，或者如果 AFK 且用户尚未响应，在原型旁边的 `NOTES.md`）。然后：

- **子形状 A** — 删除失败的变体和切换器；将获胜者折叠到现有页面中。
- **子形状 B** — 将获胜变体提升为真实路由，删除临时路由和切换器。

不要让变体组件或切换器留下来。它们很快就会腐烂并混淆下一个读者。

## 反模式

- **只在颜色或复制上不同的变体。** 那是调整，不是原型。真正的变体在结构上不同意。
- **变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 破坏目的。每个变体应该可以自由抛出布局。
- **将变体连接到真实变更。** 只读原型是可以的。如果变体需要变更，指向 stub——问题是"这应该是什么样子"，而不是"后端工作吗"。
- **直接将原型提升为生产。** 变体代码在原型约束下编写（无测试、最小错误处理）。当你将其折叠时正确重写它。
