# 原型

原型是**回答问题的可丢弃代码**。问题决定形状。

## 选择分支

识别正在回答的问题——从用户提示、周围代码，或通过询问用户（如果他们在的话）：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个tiny交互式终端应用，推动状态机通过纸上难以推理的案例。
- **"这应该是什么样子？"** → [UI.md](UI.md)。在一条路由上生成几个截然不同的 UI 变体，可通过 URL 搜索参数和浮动底部栏切换。

两个分支产生非常不同的产物——选错分支会浪费整个原型。如果问题确实是模糊的且用户无法联系，根据周围代码默认选择匹配的分支（后端模块 → logic；页面或组件 → UI）并在原型顶部说明假设。

## 两个分支都适用的规则

1. **从第一天起就是可丢弃的，并明确标记为如此。** 将原型代码放置在实际使用位置附近（它为之原型化的模块或页面旁边）——这样上下文是明显的——但命名时要让随意读者能看到它是原型，不是生产代码。对于一次性 UI 路由，遵守项目已有的路由约定；不要发明新的顶级结构。
2. **一条命令运行。** 无论项目现有任务运行器支持什么——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不持久化。** 状态存在于内存中。持久化是原型正在_检查_的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，命中一个临时数据库或一个名称明确为"PROTOTYPE — 擦除我"本地文件。
4. **跳过打磨。** 不需要测试，不需要超出使原型_可运行_的错误处理，没有抽象。目的是快速学习某事然后删除它。
5. **展示状态。** 每次操作后（logic）或每次变体切换（UI）后，打印或渲染完整相关状态，以便用户可以看到什么改变了。
6. **完成后删除或吸收。** 当原型回答了它的问题后，要么删除它，要么将验证的决策折叠到真实代码中——不要让它在仓库中腐烂。

## 完成后

原型唯一值得保留的是_答案_。将答案连同它回答的问题一起捕获到某个持久的地方（提交消息、ADR、Issue，或原型旁边的 `NOTES.md`）。如果用户在，让他进行那个捕获是快速对话；如果不在，留下占位符以便他们（或你，在下次通过时）可以在删除原型之前填写判断。
