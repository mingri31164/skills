# 深化

给定其依赖项，如何安全地深化浅模块集群。假设 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module**、**interface**、**seam**、**adapter**。

## 依赖类别

在评估深化候选者时，对其依赖进行分类。该类别决定深化模块如何跨其接缝测试。

### 1. 进程内

纯计算、内存状态、无 I/O。总是可以深化——合并模块并直接通过新接口测试。不需要适配器。

### 2. 本地可替代

具有本地测试替代品的依赖（PGLite 用于 Postgres，内存文件系统）。如果替代品存在则可深化。深化模块使用测试替代品在测试套件中运行。接缝是内部的；不在模块的外部接口处。

### 3. 远程但自有的（端口和适配器）

跨网络边界你自己的服务（微服务、内部 API）。在接缝处定义**端口**（接口）。深度模块拥有逻辑；传输作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

建议形状：_"在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器，以便逻辑即使跨网络部署也位于一个深度模块中。"_

### 4. 真正的外部（模拟）

你无法控制的第三方服务（Stripe、Twilio 等）。深化模块将外部依赖作为注入端口；测试提供模拟适配器。

## 接缝规范

- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 不要引入端口，除非至少两个适配器是合理的（通常是生产 + 测试）。单适配器接缝只是间接。
- **内部接缝 vs 外部接缝。** 深度模块可以有内部接缝（对其实现私有，由其自己的测试使用）以及其接口处的外部接缝。不要仅仅因为测试使用它们就通过接口暴露内部接缝。

## 测试策略：替换，而不是分层

- 浅模块上的旧单元测试一旦在深化模块接口上存在测试就成为废物——删除它们。
- 在深化模块接口处编写新测试。**接口就是测试表面。**
- 测试断言通过接口的可观察结果，而不是内部状态。
- 测试应该在内部重构中存活——它们描述行为，而不是实现。如果测试在实现改变时必须改变，它是在接口后面测试。

## 反模式

- 不要引入接口直到用户选择了深化候选者。深化候选者在 HTML 报告中呈现。
- 不要在用户批准之前提议接口。
- 不要将内部接缝暴露在模块的外部接口处。
