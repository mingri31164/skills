# 改进代码库架构

揭示架构摩擦并提出**深化机会**——将浅模块转变为深模块的重构。目标是可测试性和 AI 可导航性。

## 词汇表

在每个建议中精确使用这些术语。一致的语言是关键——不要漂移到"组件"、"服务"、"API"或"边界"。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块** — 任何具有接口和实现的东西（函数、类、包、切片）。
- **接口** — 调用者必须知道的一切才能正确使用模块：类型、不变量、错误模式、排序、配置。不只是类型签名。
- **实现** — 模块内部的代码。与 **适配器**不同：某物可以是一个带有大实现的小适配器（Postgres 仓库）或带有小实现的大适配器（内存 fake）。当接缝是主题时使用"适配器"；否则使用"实现"。
- **深度** — 接口上的杠杆效应：大量行为隐藏在小型接口后面。**深度** = 高杠杆。**浅** = 接口几乎和实现一样复杂。
- **接缝** —（来自 Michael Feathers）可以改变行为而不必在那个地方编辑的位置。模块接口所在的位置。在接缝处放置什么的决定本身就是设计决策，区别于接缝后面的内容。
- **适配器** — 在接缝处满足接口的具体事物。描述*角色*（它填充的插槽），而非实质（内部是什么）。
- **杠杆效应** — 调用者从深度获得什么。每个接口单位的学习，调用者获得更多能力。一个实现在 N 个调用点和 M 个测试中获得回报。
- **局部性** — 维护者从深度获得什么。变更、bug、知识集中在一个地方，而不是分散到调用方。一次修复，到处修复。

关键原则（见 [LANGUAGE.md](LANGUAGE.md) 完整列表）：

- **删除测试**：想象删除该模块。如果复杂性消失，它是直通。如果复杂性在 N 个调用方中重新出现，它是在赚取它的代价。
- **接口就是测试表面。**
- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。**

此技能由项目的领域模型_提供信息_。领域语言为好的接缝命名；ADR 记录技能不应重新争辩的决策。

## 流程

### 1. 探索

首先阅读项目的领域词汇表和你正在触及的区域的任何 ADR。

然后使用 Agent 工具和 `subagent_type=Explore` 遍历代码库。不要遵循僵化的启发式方法——有机地探索并注意你经历摩擦的地方：

- 理解一个概念需要往返于许多小模块的地方？
- 模块是**浅的**——接口几乎和实现一样复杂的地方？
- 纯函数被提取出来只是为了可测试性，但真正的 bug 藏在它们如何被调用的地方（没有**局部性**）？
- 紧耦合模块在哪里泄漏到它们的接缝？
- 代码库的哪些部分未测试，或通过当前接口难以测试？

对你怀疑是浅的任何东西应用**删除测试**：删除它会集中复杂性，还是只是移动它？"是的，集中"是你想要的信号。

### 2. 将候选者呈现为 HTML 报告

将自包含的 HTML 文件写入 OS 临时目录，这样就不会落在仓库中。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（或 Windows 上的 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，以便每次运行都获得一个新文件。为用户打开它——Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`——并告诉他们绝对路径。

报告使用 **Tailwind via CDN** 进行布局和样式，**Mermaid via CDN** 用于图表，其中图/流/序列可靠地传达结构时使用 Mermaid。将 Mermaid 与手工制作的 CSS/SVG 可视化混合——当关系是图形状时（调用图、依赖关系、序列）使用 Mermaid，当你想获得更多编辑效果时使用手工构建的 div/SVG（质量图、截面、折叠动画）。每个候选者获得一个**之前/之后可视化**。要有视觉效果。

对于每个候选者，使用相同的模板，但呈现为卡片：

- **文件** — 涉及哪些文件/模块
- **问题** — 当前架构为什么造成摩擦
- **解决方案** — 什么会改变的纯英文描述
- **收益** — 用局部性和杠杆效应解释，以及测试将如何改进
- **之前 / 之后图表** — 并排、自定义绘制，说明浅度和深化
- **建议强度** — `强烈`、`值得探索`、`推测性` 之一，呈现为徽章

在报告末尾添加**首要建议**部分：你首先处理的候选者及其原因。

**使用 CONTEXT.md 词汇表示领域，使用 [LANGUAGE.md](LANGUAGE.md) 词汇表示架构。** 如果 `CONTEXT.md` 定义了"Order"，谈论"Order 接收模块"——而不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：如果候选者与现有 ADR 矛盾，只在摩擦足够真实值得重新审视 ADR 时才呈现它。在卡片中清楚地标记（例如，警告标注：_"与 ADR-0007 矛盾——但值得重新开放，因为…"_）。不要列出 ADR 禁止的每个理论重构。

参见 [HTML-REPORT.md](HTML-REPORT.md) 获取完整 HTML 脚手架、图表模式和样式指导。

现在不要提议接口。文件写入后，询问用户："你想探索哪些？"

### 3. 深入质询循环

一旦用户选择了一个候选者，进入深入质询对话。与他们一起走设计树——约束、依赖、深化的模块形状、接缝后面是什么、哪些测试存活。

随着决策结晶，内联发生副作用：

- **用不在 `CONTEXT.md` 中的概念命名深化的模块？** 将该术语添加到 `CONTEXT.md`——与 `/grill-with-docs` 相同的规范（见 [CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md)）。如果文件不存在则惰性创建。
- **在对话中锐化模糊术语？** 立即在那里更新 `CONTEXT.md`。
- **用户以重要原因拒绝候选者？** 提供 ADR，框架为：_"你想让我将其记录为 ADR，以便未来的架构审查不再重复建议它？"_ 仅在原因对未来探索者真正需要避免重复建议相同内容时才提供——跳过短暂原因（"现在不值得"）和不言自明的原因。参见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想探索深化模块的替代接口？** 参见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
