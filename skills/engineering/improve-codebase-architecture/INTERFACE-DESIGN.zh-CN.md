# 接口设计

当用户想要探索所选深化候选者的替代接口时，使用此并行子代理模式。基于"设计两次"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 框定问题空间

在生成子代理之前，写一个用户面对的所选候选者问题空间解释：

- 任何新接口需要满足的约束
- 它将依赖的依赖项，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图来使约束具体——不是提案，只是使约束具体的方法

向用户展示这个，然后立即进入步骤 2。用户阅读和思考，而子代理并行工作。

### 2. 生成子代理

使用 Agent 工具并行生成 3+ 个子代理。每个必须为深化模块产生**截然不同**的接口。

向每个子代理提供单独的技術简报（文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 中的依赖类别、接缝后面是什么）。简报独立于步骤 1 中用户面对的问题空间解释。给每个代理不同的设计约束：

- 代理 1："最小化接口——最多 1-3 个入口点。最大化每个入口点的杠杆效应。"
- 代理 2："最大化灵活性——支持多种用例和扩展。"
- 代理 3："为主要调用方优化——使默认情况变得微不足道。"
- 代理 4（如果适用）："围绕跨接缝依赖的端口和适配器设计。"

在简报中同时包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，以便每个子代理与架构语言和项目领域语言一致地命名事物。

每个子代理输出：

1. 接口（类型、方法、参数——加上不变量、排序、错误模式）
2. 使用示例显示调用方如何使用它
3. 实现隐藏在接缝后面的是什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆效应高的地方、薄的地方

### 3. 呈现和比较

按顺序呈现设计，以便用户可以吸收每个，然后用散文比较。按**深度**（接口上的杠杆效应）、**局部性**（变更集中在哪里）和**接缝放置**对比。

在比较之后，给出你自己的建议：你认为哪个设计最强，为什么。如果不同设计的元素会很好地组合，提出混合。要固执己见——用户想要强烈的阅读，而不是菜单。
