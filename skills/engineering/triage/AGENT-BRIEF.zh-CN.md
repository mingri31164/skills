# 编写 Agent 简报

Agent 简报是在 Issue 移动到 `ready-for-agent` 时发布在 GitHub Issue 上的结构化评论。它是 AFK Agent 将使用的权威规范。原始 Issue 正文和讨论是上下文——Agent 简报是契约。

## 原则

### 耐久性优于精确性

Issue 可能坐在 `ready-for-agent` 中数天或数周。同时代码库将会改变。编写简报使其即使文件被重命名、移动或重构也保持有用。

- **做**描述接口、类型和行为契约
- **做**命名 Agent 应该寻找或修改的特定类型、函数签名或配置形状
- **不要**引用文件路径——它们会过时
- **不要**引用行号
- **不要**假设当前实现结构将保持不变

### 行为的，而不是过程的

描述系统**应该做什么**，而不是**如何实现**。Agent 将全新探索代码库并做出自己的实施决策。

- **好：** "`SkillConfig` 类型应接受类型为 `CronExpression` 的可选 `schedule` 字段"
- **坏：** "打开 src/types/skill.ts 在第 42 行添加 schedule 字段"
- **好：** "当用户运行 `/triage` 且无参数时，应看到需要关注 Issue 的摘要"
- **坏：** "在主处理程序函数中添加 switch 语句"

### 完整的验收标准

Agent 需要知道何时完成。每个 Agent 简报必须有具体、可测试的验收标准。每个标准应可独立验证。

- **好：** "运行 `gh issue list --label needs-triage` 返回经过初步分类的 Issue"
- **坏：** "分类应该正确工作"

### 明确的范围边界

陈述什么不在范围内。这阻止 Agent 过度设计或对相邻功能做出假设。

## 模板

```markdown
## Agent 简报

**类别：** bug / enhancement
**摘要：** 需要发生什么的一行描述

**当前行为：**
描述现在发生什么。对于 bug，这是损坏的行为。对于增强，这是功能构建的现状。

**期望行为：**
描述 Agent 工作完成后应该发生什么。对边缘情况和错误条件要具体。

**关键接口：**
- `TypeName` — 需要改变什么及为什么
- `functionName()` 返回类型 — 当前返回什么 vs 应该返回什么
- Config 形状 — 任何需要的新配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**范围之外：**
- 不应在此 Issue 中更改或解决的事情
- 可能看起来相关但实际上是分开的相邻功能
```
