# 分类

将项目 Issue 追踪器上的 Issue 通过分类角色的小状态机移动。

在分类期间发布到 Issue 追踪器的每条评论或 Issue **必须**以此免责声明开头：

```
> *这是 AI 在分类期间生成的。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久的 Agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库如何工作

## 角色

两个**类别**角色：

- `bug` — 某物坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 完全指定，准备好供 AFK Agent 拾取
- `ready-for-human` — 需要人工实现
- `wontfix` — 将不会被处理

每个分类后的 Issue 应该正好携带一个类别角色和一个状态角色。如果状态角色冲突，标记它并在做任何其他事情之前询问维护者。

这些是规范角色名称——Issue 追踪器中使用的实际标签字符串可能不同。映射应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：未标记的 Issue 通常首先进入 `needs-triage`；从那里它可以移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖——标记看起来不寻常的转换并在继续之前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解释请求并采取行动。示例：

- "给我看任何需要我注意的东西"
- "让我们看看 #42"
- "将 #42 移到 ready-for-agent"
- "有什么准备好让 Agent 拾取的？"

## 显示需要关注的内容

查询 Issue 追踪器并按时间顺序呈现三个桶：

1. **未标记** — 从未分类。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info`，且自上次分类笔记以来有报告者活动** — 需要重新评估。

显示每个 Issue 的计数和一行摘要。让维护者选择。

## 对特定 Issue 进行分类

1. **收集上下文。** 阅读完整 Issue（正文、评论、标签、报告者、日期）。解析任何先前的分类笔记，这样你就不会重复问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的 ADR。阅读 `.out-of-scope/*.md` 并呈现任何类似于此 Issue 的先前拒绝。

2. **推荐。** 告诉维护者你的类别和状态推荐及推理，加上与 Issue 相关的简要代码库摘要。等待指示。

3. **复现（仅限 bug）。** 在任何深入质询之前，尝试复现：阅读报告者的步骤，追踪相关代码，运行测试或命令。报告发生了什么——代码路径成功复现、复现失败或细节不足（强烈的 `needs-info` 信号）。确认的复现使 Agent 简报强得多。

4. **深入质询（如需要）。** 如果 Issue 需要充实，运行 `/grill-with-docs` 会话。

5. **应用结果：**
   - `ready-for-agent` — 发布 Agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 与 Agent 简报相同的结构，但注明为什么不能委托（判断调用、外部访问、设计决策、手动测试）。
   - `needs-info` — 发布分类笔记（模板如下）。
   - `wontfix`（bug）— 礼貌解释，然后关闭。
   - `wontfix`（增强）— 写入 `.out-of-scope/`，从评论链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用角色。如果有部分进展，可选择添加评论。

## 快速状态覆盖

如果维护者说"将 #42 移到 ready-for-agent"，相信他们并直接应用角色。确认你即将做什么（角色变更、评论、关闭），然后采取行动。跳过深入质询。如果要在没有深入质询会话的情况下移动到 `ready-for-agent`，询问他们是否要写 Agent 简报。

## Needs-info 模板

```markdown
## 分类笔记

**到目前为止我们已经确定的：**

- 要点 1
- 要点 2

**我们仍然需要你提供的（@报告者）：**

- 问题 1
- 问题 2
```

将在深入质询期间解决的所有内容捕获到"到目前为止已确定"下，这样工作不会丢失。问题必须是具体和可操作的，而不是"请提供更多信息"。

## 恢复先前的会话

如果 Issue 上存在先前的分类笔记，阅读它们，检查报告者是否回答了任何悬而未决的问题，并在继续之前呈现更新后的图景。不要重复问已解决的问题。
