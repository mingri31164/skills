# 审查

对 `HEAD` 和用户提供的固定点之间的差异进行两轴审查：

- **标准** — 代码是否符合此仓库的编码标准？
- **规范** — 代码是否忠实实现了原始 Issue / PRD / 规范？

两个轴作为**并行子 Agent** 运行，这样它们不会相互污染上下文，然后此技能聚合它们的发现。

Issue 追踪器应该已经提供给你——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定点

无论用户说什么是固定点——提交 SHA、分支名称、标签、`main`、`HEAD~5` 等。不要固执己见；直接传递。如果他们没有指定，问："针对什么审查——分支、提交还是 `main`？"在没有得到之前不要继续。

捕获一次 diff 命令：`git diff <fixed-point>...HEAD`（三点，这样比较是针对合并基准的）。还通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

### 2. 识别规范来源

按此顺序寻找原始规范：

1. 提交消息中的 Issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的 PRD/规范文件。
4. 如果什么都没找到，询问用户规范在哪里。如果他们说没有，**规范**子 Agent 将跳过并报告"无规范可用"。

### 3. 识别标准来源

代码库中记录代码编写方式的任何内容。常见位置：

- `CLAUDE.md`、`AGENTS.md`
- `CONTRIBUTING.md`
- `CONTEXT.md`、`CONTEXT-MAP.md`、每个上下文的 `CONTEXT.md` 文件
- `docs/adr/`（架构决策是标准）
- `.editorconfig`、`eslint.config.*`、`biome.json`、`prettier.config.*`、`tsconfig.json`（机器强制标准——注意它们但不要重新检查工具已经检查的内容）
- 仓库根目录或 `docs/` 下的任何 `STYLE.md`、`STANDARDS.md`、`STYLEGUIDE.md` 或类似文件

收集文件列表。**标准**子 Agent 将阅读它们。

### 4. 并行生成两个子 Agent

发送带有两个 `Agent` 工具调用的单条消息。两个都使用 `general-purpose` 子代理。

**标准子 Agent 提示** — 包括：

- 完整的 diff 命令和提交列表。
- 你在步骤 3 中找到的标准源文件列表。
- 简报："阅读标准文档。然后阅读 diff。报告——每个相关文件/hunk 处——diff 违反文档化标准的每个地方。引用标准（文件 + 规则）。区分硬性违规和判断调用。跳过工具强制的内容。400 词以内。"

**规范子 Agent 提示** — 包括：

- diff 命令和提交列表。
- 规范的路径或获取的内容。
- 简报："阅读规范。然后阅读 diff。报告：(a) 规范要求的缺失或部分要求；(b) diff 中未被要求的超出范围行为；(c) 看起来已实现但实现看起来错误的要求。为每个发现引用规范行。400 词以内。"

如果规范缺失，跳过规范子 Agent 并在最终报告中注明。

### 5. 聚合

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，原样或轻度清理。不要合并或重新排名发现——两个轴是故意分开的，这样用户可以独立看到它们。

以一行摘要结束：每个轴的发现总数，以及标记的最严重单个问题（如果有）。

## 为什么是两个轴

变更可以一个轴通过而另一个失败：

- 遵循每个标准但实现错误的东西 → **标准通过，规范失败。**
- 精确做了 Issue 要求但违反项目约定的代码 → **规范通过，标准失败。**

分开报告可以阻止一个轴掩盖另一个。
